# Preventing race conditions in rapid photo storage for ADHD users

Race conditions during rapid photo additions create a perfect storm of technical failures and user frustration, especially for ADHD users who exhibit hyperfocus behaviors and low tolerance for delays. This research synthesizes architectural patterns, implementation strategies, and ADHD-specific design considerations to achieve zero data loss, prevent crashes, and provide the sub-100ms feedback that these users require.

## The anatomy of photo storage race conditions

When multiple photos are added rapidly to activity cards, race conditions manifest through several critical failure patterns. The most common occurs when **multiple threads simultaneously check filename existence** before saving - Thread A and B both verify a filename doesn't exist, both proceed to save using that filename, resulting in data corruption or loss. In React Native specifically, setState race conditions compound this problem when multiple photo operations trigger simultaneous state updates, with memory pressure during rapid additions causing components to unmount mid-operation.

SQLite's locking hierarchy reveals why these failures cascade. With only **one writer allowed at a time** through database-level locking, concurrent photo operations create a bottleneck where the EXCLUSIVE lock blocks all other operations. Performance metrics show that while SQLite handles blobs under 100KB efficiently (35% faster than filesystem storage), the single-writer limitation means application-level queuing becomes essential. Memory overhead compounds the problem - each 12MP photo consumes **approximately 40MB uncompressed in memory**, while older iOS devices crash at just 23MB total memory usage.

The failure rate increases exponentially when concurrent operations exceed 6-8 browser connection limits. Mobile apps show particular vulnerability during burst photo capture scenarios, where ADHD users' hyperfocus behaviors can lead to 40-50+ rapid captures. Without proper synchronization, these scenarios trigger cascading failures: SQLITE_BUSY errors, component unmounting during uploads, and ultimately app crashes that lose user data.

## ADHD-optimized architectural design

Understanding ADHD-specific behaviors fundamentally changes how we approach the solution architecture. Research shows ADHD users experience **hyperfocus states with increased prefrontal activity**, leading to rapid successive actions without waiting for system feedback. Their dopamine-seeking behavior means delays feel punishing, while working memory limitations (particularly visual working memory) make it difficult to track upload states across multiple photos.

The solution requires a **three-layer architecture** that provides immediate visual feedback while handling async operations gracefully:

```
User Interface Layer (Optimistic UI)
├── Instant preview grid (<100ms feedback)
├── Determinate progress bars (not spinners)
└── Non-blocking visual confirmations

Queue Management Layer
├── Priority-based processing (PQueue)
├── Exponential backoff with jitter
└── Memory-aware concurrency limits

Persistence Layer
├── IndexedDB for temporary storage
├── SQLite for metadata (<100KB)
└── Filesystem for large blobs (>1MB)
```

The optimistic UI pattern proves essential for ADHD users. By displaying photos immediately in the grid with a subtle uploading indicator, users receive the instant gratification their brains require. Progress must be **determinate rather than indeterminate** - showing exact upload percentage prevents anxiety about whether the system is working. Visual feedback uses calming colors (pastels, greens, blues) with adequate white space to prevent sensory overload.

Memory management becomes critical given the 40MB per photo overhead. The architecture implements **streaming uploads with 5-10MB chunks**, preventing full image loading into memory. A hybrid storage approach routes photos based on size - metadata and thumbnails to SQLite for fast queries, full images to filesystem with database references. This prevents the linear performance degradation that occurs beyond 100 concurrent blob operations in pure database storage.

## Implementation guidelines and patterns

### Queue management for zero data loss

The queue implementation must balance performance with reliability while providing immediate user feedback:

```javascript
import PQueue from 'p-queue';
import { retryWithExponentialBackoff } from './utils';

class PhotoUploadManager {
  constructor() {
    this.uploadQueue = new PQueue({
      concurrency: 2, // Limit based on device memory
      timeout: 30000,
      throwOnTimeout: true
    });
    
    this.memoryMonitor = new MemoryPressureMonitor({
      threshold: 0.8, // 80% memory usage
      onPressure: () => this.uploadQueue.concurrency = 1
    });
  }
  
  async addPhoto(imageData, metadata) {
    const tempId = generateTempId();
    
    // Immediate optimistic UI update
    this.updateUI({
      id: tempId,
      status: 'uploading',
      preview: await createThumbnail(imageData),
      progress: 0
    });
    
    // Queue with retry logic
    return this.uploadQueue.add(
      () => this.uploadWithRetry(imageData, tempId, metadata),
      { priority: metadata.priority || 0 }
    );
  }
  
  async uploadWithRetry(imageData, tempId, metadata, attempt = 1) {
    try {
      const chunks = await this.chunkImage(imageData);
      const uploadSession = await this.createUploadSession();
      
      for (const [index, chunk] of chunks.entries()) {
        await this.uploadChunk(uploadSession, chunk);
        this.updateProgress(tempId, (index + 1) / chunks.length * 100);
      }
      
      const result = await this.finalizeUpload(uploadSession);
      this.replaceOptimisticData(tempId, result);
      return result;
      
    } catch (error) {
      if (attempt < 3 && this.isRetryable(error)) {
        const delay = Math.pow(2, attempt) * 1000 + Math.random() * 1000;
        await sleep(delay);
        return this.uploadWithRetry(imageData, tempId, metadata, attempt + 1);
      }
      
      this.handleFailure(tempId, error);
      throw error;
    }
  }
}
```

### Transaction patterns for atomic operations

Ensuring atomicity across the multi-step upload process requires careful transaction management:

```javascript
class TransactionalPhotoStorage {
  async savePhotoWithMetadata(localUri, metadata) {
    const db = await this.getDatabase();
    
    return db.transaction(async (tx) => {
      // 1. Create photo record
      const photoId = await tx.executeSql(
        'INSERT INTO photos (local_uri, status) VALUES (?, ?)',
        [localUri, 'pending']
      );
      
      // 2. Create upload queue entry
      await tx.executeSql(
        'INSERT INTO upload_queue (photo_id, priority) VALUES (?, ?)',
        [photoId, metadata.priority || 0]
      );
      
      // 3. Store temporary data in IndexedDB
      await this.indexedDB.transaction(['temp_uploads'], 'readwrite')
        .objectStore('temp_uploads')
        .put({
          photoId,
          chunks: [],
          uploadedAt: Date.now()
        });
      
      return photoId;
    });
  }
}
```

### Error recovery with ADHD-friendly messaging

Error handling must avoid blame-inducing language while providing clear recovery paths:

```javascript
const ADHDFriendlyErrorHandler = {
  handleUploadError(error, context) {
    const errorMap = {
      'NetworkError': {
        message: "Internet hiccup! Your photos are safe - we'll retry in a moment",
        icon: '🔄',
        action: 'automatic-retry'
      },
      'QuotaExceededError': {
        message: "Almost out of space! Let's make room for your creativity",
        icon: '📦',
        action: 'show-storage-manager'
      },
      'TimeoutError': {
        message: "Taking a bit longer than usual - still working on it!",
        icon: '⏳',
        action: 'show-progress'
      }
    };
    
    const errorInfo = errorMap[error.name] || {
      message: "Something unexpected happened - let's try a different approach",
      icon: '🔧',
      action: 'show-alternatives'
    };
    
    return {
      ...errorInfo,
      supportingText: "Your photos are safe in temporary storage",
      primaryAction: this.getRecoveryAction(errorInfo.action),
      secondaryAction: { label: 'I'll handle it later', action: 'defer' }
    };
  }
};
```
